# Бэкенд «Полки»

Самостоятельный сервис: HTTP API, подбор рецептов с Z.ai, каталоги рецептов и пищевой ценности. Не зависит от исходников фронтенда или бота. Общие типы и Telegram-авторизация находятся в `../../shared`.

## Запуск

Node.js 22.22.2+. Из корня монорепозитория:

```sh
npm ci
npm run dev:backend
```

API: `http://127.0.0.1:8788/api/health`. Корневой `.env` читается только сервером. `PORT` и `HOST` необязательны. `API_GLM` нужен только для запросов к ИИ, для чтения каталогов ключ не нужен.

Обычный `npm run dev` по-прежнему запускает фронтенд с теми же обработчиками API внутри Vite. Отдельно поднимать бэкенд в этом режиме не требуется.

Для явного обхода авторизации ИИ при локальном запуске отдельного сервиса:

```sh
BACKEND_LOCAL_DEV=1 npm run dev:backend
```

Обход работает только при loopback-привязке сервера и loopback-подключении. В облачной функции он не применяется. В опубликованном сервисе нужны `AI_TEST_CODE` или серверный `BOT_TOKEN`, а также разрешённый `ALLOWED_ORIGIN`. CORS не заменяет авторизацию.

## API

- `GET /api/health` — состояние сервиса и размеры каталогов.
- `GET /api/catalog/recipes?q=гречка&limit=20&offset=0` — поиск по названию/тексту ингредиентов, с пагинацией. Есть оригинальное название и `nameRu`.
- `GET /api/catalog/recipes/bc-merchants-buckwheat` — один исходный рецепт.
- `GET /api/catalog/products?q=творог&limit=20&offset=0` — поиск товаров по словам в названии и бренде.
- `GET /api/catalog/products?barcode=4600000000000` — точное совпадение штрихкода, если оно есть. Пример кода иллюстративный.
- `POST /api/ai/receipt` — `{ image: "data:image/jpeg;base64,..." }`, фото/скриншот покупок, результат для подтверждения; лимит JSON 4,1 МБ, вложение до 3 МБ. Модель `glm-4.6v-flash`, без платного fallback.
- `POST /api/ai/recipes` — проверяемый запрос подбора по запасам, времени, пожеланиям и исключениям.

`limit` от 1 до 100. Запись в общий каталог через публичный API не разрешена. Результат поиска не считается подтверждением совпадения товара из чека. Нельзя молча заменять неизвестный продукт похожим брендовым товаром.

Настоящие аккаунты хранят полку, готовые блюда, дневник, личные продукты и профиль в PostgreSQL через `/api/state`. Деморежим хранится отдельно локально. Архитектура и перенос прежних записей — [USER_DATA.md](../../USER_DATA.md).

## Данные и границы точности

Каталоги — версионируемые JSON-файлы в `data/`, загружаемые сервером. Для этого объёма не нужна новая СУБД или платный сервис. При появлении проверяемого общего пользовательского каталога можно заменить repository, сохранив API.

### Рецепты

100 разных рецептов с [Based Cooking](https://github.com/LukeSmithxyz/based.cooking). У проекта [Unlicense / public domain](https://github.com/LukeSmithxyz/based.cooking/blob/master/LICENSE.md). Лицензия сохранена в `data/sources/`.

У каждой записи есть оригинальный Markdown, ингредиенты и шаги, исходный URL, дата загрузки и SHA-256 исходного текста. Русские названия в `recipe-names.ru.json` добавлены для поиска. **Тексты ингредиентов и инструкций пока на языке оригинала — английском.** Это справочная база для ИИ: модель получает до шести подходящих источников и составляет русский рецепт под реальные запасы. Это не 100 готовых русских карточек интерфейса и не 100 рецептов с выверенными граммовками.

Неоднозначные чашки/штуки не выданы за точные граммы. Времена, масса, КБЖУ и фотографии не выдуманы при импорте. Существующие фотографии фронтенда сохранены; в локальном каталоге пять рецептов, два омлета используют одно фото с пометкой варианта подачи. Импортированные рецепты кулинарно не тестировались.

### Продукты

302 русскоязычных товара из выборки Open Food Facts по стране продажи Russia, со штрихкодом, брендом, КБЖУ и ссылкой. Это начальная выборка, не весь ассортимент России и не выгрузка «Пятёрочки» или «Перекрёстка».

Импорт отклоняет неполные/нечисловые/отрицательные нутриенты, невозможные значения БЖУ, неподходящие штрихкоды и записи без русского названия. Значения не восстанавливаются догадками ИИ. Проверка структуры не гарантирует правильность самой пользовательской записи: `verification: community-unverified` сохраняется в каждой карточке. Перед использованием конкретного товара нужно подтвердить соответствие упаковке. Значения `per100` переданы как в источнике; обозначение `basis` предупреждает, что 100 г и 100 мл нельзя автоматически считать взаимозаменяемыми.

Источник: [Open Food Facts API](https://openfoodfacts.github.io/openfoodfacts-server/api/). Каталог на [ODbL-1.0](https://opendatacommons.org/licenses/odbl/1-0/), отдельные данные — [DbCL-1.0](https://opendatacommons.org/licenses/dbcl/1-0/). Производная выборка `products.openfoodfacts.json` распространяется на условиях ODbL с указанием Open Food Facts. Атрибуция возвращается API; при показе этих данных во фронтенде её необходимо сохранить. Фотографии товаров не скачивались. Личные пользовательские данные с этим открытым каталогом не смешиваются.

### Приоритет продуктов

`shared/perishability.ts` содержит категории и грубые ориентиры для ранжирования, а не даты годности. Для известных названий работают локальные правила; ИИ дополнительно определяет скоропортящиеся продукты в запросе подбора. Его подсказки принимаются только для известных id из запроса и не переопределяют известные категории консервированных/замороженных продуктов.

Исключения фильтруют доступные продукты до генерации. Пожелания передаются модели с явным приоритетом над использованием скоропортящихся продуктов. Семантическое выполнение произвольного пожелания зависит от модели; отдельного универсального валидатора естественного языка нет. После проверки состава сервер сортирует предложения по скоропортимости с дополнительным приоритетом старых запасов по `addedAt`. Дата добавления необязательна; возраст неизвестных дат не выдумывается. Даты истечения срока не вычисляются и не обещаются. Время запроса ИИ `maxMinutes` — целое число от 5 до 2880 минут. Обычное поле на главной ограничено 5–360 минутами; при адаптации выбранного долгого рецепта используется его время из каталога.

## Повторный импорт

```sh
python3 apps/backend/scripts/import-catalogs.py
```

Запуск из корня, требуется интернет и Python 3. Скрипт скачивает выбранные рецепты и максимум три страницы по 100 товаров, с паузами и ограниченными повторами при 429/5xx. Кэш загрузок — `/private/tmp/polka-catalog-import`. Для массового расширения использовать официальный bulk export Open Food Facts, а не обходить десятки тысяч карточек запросами поиска. Импорт ничего не пишет во внешние сервисы. Отчёт: `data/import-report.json`.

## Сборка и размещение

Для совместного размещения фронтенда и API в Timeweb используй корневой [Dockerfile](../../Dockerfile) и [DEPLOYMENT.md](../../DEPLOYMENT.md). Переменная `WEB_DIST` включает отдачу только указанной папки клиентской сборки, `APP_ORIGIN` задаёт публичный origin без доверия к входному Host. Если `WEB_DIST` не задан, сервер сохраняет режим отдельного API. Двоичные файлы передаются потоком; неизвестные `/api/...` не подменяются HTML. Миграции БД запускаются явно, отдельно от старта сервера.

```sh
npm run build:backend
```

Результат — `apps/backend/dist/`, без `.env` и runtime-зависимостей. Для Node-сервиса: `node apps/backend/dist/server.cjs`. Для Yandex Cloud Functions: загрузить содержимое `dist/`, точка входа `index.handler`, Node.js 22.22.2+.

Прямой POST на URL функции сохраняет прежний маршрут ИИ. Для каталогов у прямого URL функции можно использовать `?route=/api/catalog/recipes`; через API Gateway передавать путь `/api/...`.

Ничего не опубликовано автоматически. `npm run build:ai` оставлен как совместимый псевдоним новой сборки. Лимиты запросов к ИИ остаются в памяти экземпляра, как и раньше; это не распределённый лимитер.

Чтение таблицы пищевой ценности на упаковке и пополнение общего каталога пользователями пока не реализованы.

Распознавание не создаёт пользовательских записей на сервере и не сохраняет фото. Количество неизвестно — возвращается null; обычные русские единицы приводятся к общему формату. Граммы вычисляются только из явной массы. КБЖУ кандидатов берутся из каталогов, а не генерируются. Подсказки из открытого каталога требуют проверки упаковки. Лимиты запросов и авторизация общие для текста и фото; не логировать тела запросов или изображения.

При размещении функции учитывайте ожидание модели до 65 секунд: внешний HTTP-таймаут должен позволять дождаться ответа. Значения окружения и настройки внешних сервисов автоматически не меняются.

## Ошибки и устойчивость ИИ

`ai/zai.ts` разбирает код ошибки Z.ai: `1305` — перегрузка, `1302` — частота/параллельные запросы, `1113`/ошибки доступа — подключение ключа, отдельные коды — квота. Все HTTP 429 больше не выдаются за перегрузку. Исходные тела ошибок, ключ и фото в ответ клиенту не включаются. При временном отказе выполняется один повтор через 1,6 секунды в пределах общего таймаута попыток. Платные модели и платный fallback не используются.

Названия продуктов из ответа сопоставляются только с однозначно известными продуктами запроса; явные числовые строки вроде `"200 г"` нормализуются. Неизвестные продукты и превышение запасов не принимаются. Невалидный рецепт отбрасывается целиком, его ингредиенты не удаляются по одному. Если все варианты не прошли проверку, выполняется один запрос исправления к той же бесплатной модели. Явное пожелание «из творога» становится обязательным продуктом при одном однозначном совпадении на полке.

Отмена HTTP-запроса передаётся в вызов Z.ai в локальном Vite и отдельном Node-сервере; активный слот освобождается в `finally`. В облачной функции физическое прерывание зависит от платформы. Максимальное ожидание распознавания — 65 секунд; подбор с исправлением может занимать до 110 секунд. Для облачного HTTP-таймаута нужно учитывать этот предел; настройки облака автоматически не меняются.

При реальной диагностике 7 ноября 2026 запрос завтрака из творога вернул три проверенных рецепта. Vision-модель в том же сеансе возвращала `1305` (в том числе после одного повтора): это подтверждённый отказ внешнего сервиса, а не обещание исправленной доступности.

### API новой библиотеки

- `POST /api/library/search` — публичный поиск в открытом каталоге, без ИИ-ключа. Поля: `query`, `category`, `maxMinutes` (0 — любое время), `sort` (`relevance`, `quick`, `calories`), `offset`, `limit` (1–24), `exclusions`, `products`. Ответ: `items`, `total`, `catalogTotal`, `offset`, `limit`. Поиск не ограничивается 3 или 6 рецептами; каждая следующая страница доступна до конца результатов.
- `GET /api/library/recipes/ut-<slug>` — полный русский рецепт.
- `GET /api/health` дополнительно возвращает `libraryRecipes: 501`.

Поиск — локальные лексические правила по названию/составу, категориям, времени, исключениям и нескольким явным диетическим признакам, не универсальное понимание свободного текста. Совпадения с полкой используются для ранжирования по названиям; они не подтверждают достаточность массы или эквивалентность сортов. Приоритет по давности скоропортящихся запасов сохраняется. Продукты для поиска агрегируются, старые сроки годности/профиль/дневник не передаются. Пользовательские поисковые данные на сервере не сохраняются.

Кнопка подготовки исходного рецепта передаёт `referenceRecipeId` в ИИ. Сервер сам находит соответствующий источник; новые неизвестные продукты/избыточные количества не принимаются. Адаптированный вариант проходит прежнюю проверку и получает КБЖУ, рассчитанное по продуктам пользователя. Чтение исходного рецепта само по себе не списывает ингредиенты и не создаёт приём пищи.

## Автоподстановка пищевой ценности

`shared/nutritionMatching.ts` — общий слой сопоставления. Брендовая база содержит 302 полные записи, типовой каталог — 50 продуктов. Расширение OFF выполняет `scripts/import-products.py`: три небольшие категории российского рынка, до 300 исходных строк, паузы, ограниченные повторы 429/5xx, слияние по штрихкоду без удаления прежней выборки. Отчёт с URL и SHA-256 — `data/nutrition-import-report.json`. Это начальная выборка, не весь ассортимент РФ. Для большого дальнейшего импорта нужен официальный bulk export OFF. Лицензии ODbL/DbCL и непроверенное происхождение сообщества сохраняются.

37 новых типовых овощей и фруктов — фактические значения из двух таблиц FDA: [фрукты](https://www.fda.gov/food/nutrition-food-labeling-and-critical-foods/raw-fruits-poster-text-version-accessible-version), [овощи](https://www.fda.gov/food/nutrition-food-labeling-and-critical-foods/nutrition-information-raw-vegetables). Исходные массы и КБЖУ порций, URL и правило перевода сохранены в `shared/data/produce-fda.json`. Значения пересчитаны пропорционально на 100 г с округлением до одного знака; сами исходные таблицы уже округлены. Это приблизительные типовые значения для сырых продуктов, не брендовая маркировка и не лабораторная точность. Прежние 13 типовых значений и пользовательские данные не заменены.

Матчер не использует память модели для нутриентов: удаляет вес упаковки из поискового имени, нормализует пунктуацию/регистр, проверяет указанную жирность, оценивает полноту совпадения названия/бренда и неоднозначность. Уверенный кандидат помечается `confidence: exact` и выбирается автоматически. Совпадение только по общему типу не объявляется конкретной упаковкой: используется явно типовой продукт либо предлагается выбор. Йогурт не совпадает с огурцом по подстроке. Соки, консервы, маринады, вкусовой йогурт и продукты другой указанной жирности не получают нутриенты сырого/другого типового аналога.

`GET /api/catalog/nutrition-match?q=<название>` возвращает найденные варианты без обращения к Z.ai, а также размеры обеих баз. Этот же матчер используется сразу после OCR. Для продуктов с однозначной твёрдой категорией источник трактуется на 100 г; для жидкостей и неясных категорий подтверждение единиц остаётся обязательным. Поля КБЖУ в форме чека появляются только при ручном выборе ввода с упаковки. Проверка и сохранение всего чека остаются атомарными.

Введённый пользователем новый продукт сохраняется в его личном состоянии (PostgreSQL для аккаунта, localStorage для демо) и повторно подставляется при следующем точном совпадении. Неопределённые масса, упаковка или единицы по-прежнему требуют уточнения. Личные продукты не отправляются в открытую общую базу. Распознавание фото зависит от доступности внешней vision-модели; увеличение справочника не устраняет её перегрузку.

## Подбор через ИИ по нашей базе

На главной сначала вызывается `POST /api/ai/recipes` с `task: "search"` и обычным контекстом полки. `ai/search.ts` использует бесплатную `glm-4.7-flash` (при временной перегрузке — резервную `glm-4.5-flash`) для перевода свободного пожелания в структурированный поиск: название блюда, обязательные ингредиенты, исключения, категория, диета, сортировка. Модель не возвращает придуманные карточки. `shared/aiRecipeSearch.ts` проверяет ответ; время и ограничения профиля остаются под контролем кода. Обязательный выбранный продукт нельзя убрать ответом модели.

Затем обычный слой каталога выполняет структурированный поиск по всем 501 рецептам. `requiredIngredients` проверяются по составу, а не только названию. Первые три карточки — лишь превью; остальные доступны страницами без дополнительных вызовов ИИ. При недоступности модели показывается ошибка, вместо незаметного перехода к обычному поиску по исходной фразе.

Если точной выдачи нет, адаптация использует до шести настоящих рецептов из того же русского каталога. Каждый результат должен ссылаться на переданный `referenceRecipeId`; неизвестный ID отклоняется, атрибуция берётся из базы, а не ответа модели. При открытии исходного рецепта работает прежняя явная адаптация выбранного блюда. Ингредиенты, доступные массы, обязательные продукты и КБЖУ по-прежнему проверяются/рассчитываются кодом. История поведения не используется для персонализации топ-3. Публикация обновлённого бэкенда выполняется отдельно.

Резерв разбора пожеланий: не более двух вызовов по 25 секунд, без повторов одной и той же модели. Резерв используется при временной перегрузке, сетевом сбое, таймауте или некорректном плане. При ошибке доступа к ключу, квоте аккаунта или отмене пользователя переключения нет. Обе модели проходят один и тот же валидатор; платные модели и обычный лексический поиск вместо ИИ не подключаются. При недоступности обеих возвращается ошибка. Приготовление и распознавание чеков этот резерв не затрагивает.

## Аккаунты и PostgreSQL

Слой `src/db` управляет пулом и явными миграциями; `src/accounts` содержит хранилище пользователей/сессий и HTTP-маршруты. SQL-запросы с данными пользователя параметризованы. Создание/обновление пользователя и сессии выполняется одной транзакцией. В ответах не раскрываются тексты SQL, строки подключения и внутренние ошибки. Сырой Telegram initData и исходный токен сессии в базе не хранятся.

- `POST /api/auth/telegram`, JSON `{ "initData": "..." }`: проверяет подпись и давность, создаёт/находит аккаунт, выдаёт host-only HttpOnly cookie, публичный профиль и сессионный токен только для памяти приложения (поддержка Telegram-фреймов без cookies). Фронтенд не может назначить себе произвольный Telegram ID.
- `GET /api/me`: возвращает только владельца действующей сессии (cookie либо Bearer), иначе 401. Профиль не кешируется.
- `POST /api/auth/logout`, JSON `{}`: отзывает текущую сессию и очищает cookie. Другие сессии не затрагиваются.

Нужны серверные `DATABASE_URL` и `BOT_TOKEN`. Не включайте `BACKEND_LOCAL_DEV` в облаке; для аккаунтов даже в локальном режиме подпись Telegram обязательна. Настройте `ALLOWED_ORIGIN` на точный origin приложения. Для аккаунтов используйте один origin с API под `/api`; междоменные cookie и режим входа вне Telegram пока не предусмотрены.

Для миграций из корня: `npm run db:migrate`. Сборка копирует версионированные SQL в backend/dist/migrations; мигратор проверяет SHA-256, блокирует параллельное применение и откатывает неуспешную миграцию. Перенос пользовательских записей реализован с подтверждением; развёртывание, TLS к облачной БД и настройка облачных резервных копий ещё не выполнены.
