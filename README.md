# Полка — Telegram Mini App

Приложение про свои продукты, выбор рецептов и дневник КБЖУ. В настоящем Telegram-аккаунте полка, дневник и профиль хранятся в PostgreSQL. Внешняя публикация фронтенда, API и бота выполняется отдельно; команды сборки ничего не публикуют.

Для Timeweb подготовлен [Dockerfile](Dockerfile): один контейнер отдаёт фронтенд и API. Настройки для **polka.net.ru**, переменные сервера, миграции и границы готовности — в [DEPLOYMENT.md](DEPLOYMENT.md). Деплой автоматически не выполняется.

## Структура сервисов

- `apps/web` — React, TypeScript, Vite; фронтенд для браузера и Telegram Mini App.
- `apps/backend` — отдельный HTTP API, подбор с Z.ai, каталоги рецептов и пищевой ценности. [Подробности бэкенда](apps/backend/README.md).
- `apps/bot` — существующий Telegram-бот на Cloudflare Workers. Его старые серверные напоминания используют D1; настройки облака в этой задаче не менялись. Функции бота можно развивать независимо от API.
- `shared` — общие типы, контракт ИИ, категории скоропортимости, проверка Telegram initData.
- `tests` — проверки расчётов, хранения, интерфейса, авторизации и API.

Бэкенд не импортирует код фронтенда или бота. Фронтенд и бэкенд используют общие контракты. Интерфейс подключён к проверенному Telegram-входу, сессиям и пользовательскому хранилищу PostgreSQL. Настройка и границы готовности описаны ниже.

## Локальный запуск

Нужен Node.js **22.22.2+**: установленный системный Node 20 не подходит текущим зависимостям UI-тестов. `.nvmrc` указывает ветку 22.

```sh
npm ci
npm run dev
```

Открой адрес Vite из терминала (обычно `http://localhost:5173`). В режиме разработки `/api/ai/recipes` и `/api/catalog/...` обрабатываются сервером Vite; ключ и серверные каталоги не включаются в клиентскую сборку.

Локальный и опубликованный интерфейсы используют вход через Telegram. При открытии в браузере без сессии появляется ссылка на бота. В аккаунте нового пользователя полка и дневник пустые.

Для подбора ИИ и распознавания чеков задай `TIMEWEB_AI_TOKEN` в **корневом `.env`**. Образец — `.env.example`. Никогда не помещай ключ в `VITE_*`, исходники, Git или сообщения. После изменения `.env` перезапусти dev-сервер. Без ключа локальные рецепты, полка и дневник доступны.

Отдельный сервис API:

```sh
npm run dev:backend
```

По умолчанию `http://127.0.0.1:8788/api/health`. Чтение каталогов не требует ключа. Для локальных ИИ-запросов без Telegram: `BACKEND_LOCAL_DEV=1 npm run dev:backend` (только loopback).

## Реализовано

- Четыре раздела: Главная с подбором рецептов, Полка, Дневник, Профиль; отдельные формы и Telegram BackButton во внутренних сценариях.
- Полка с граммовками, редактированием, удалением, подбором рецептов по продукту и разделом готовой еды.
- Срок годности и метки скоропортимости не показываются. Подходящие рецепты с более старыми скоропортящимися запасами получают внутренний приоритет по дате добавления. Для старых запасов без даты возраст не выдумывается. Это рекомендация порядка использования, не гарантия свежести.
- Пять локальных рецептов с существующими фотографиями в подборке, изменение состава/количеств, создание своего блюда. Рецепт открывается отдельной страницей без фото и блока источников; ссылка вида `#recipe=omelet` поддерживает обновление страницы на GitHub Pages.
- Калькулятор порций (1–50) пересчитывает ингредиенты и КБЖУ. Показаны значения на порцию и на всё блюдо, нехватка продуктов с количеством. Все шаги видны сразу нумерованным списком, выполненные можно отметить; списание выполняется отдельным подтверждением готовности блюда.
- Для подходящих продуктов доступны штуки, ложки, стаканы и миллилитры. Расчёты и запасы остаются в граммах, бытовые меры обозначены как приблизительные. Правила и источники — [MEASUREMENTS.md](MEASUREMENTS.md). Вес порции в граммах показывается с «≈» по расчётному выходу. Взвешенный готовый выход можно указать отдельно — он заменит оценку; непроверенные коэффициенты и ограничения описаны в MEASUREMENTS.md.
- Приготовление списывает сырые ингредиенты и создаёт готовое блюдо. Запись съеденной доли уменьшает остаток блюда, не списывая ингредиенты повторно.
- Дневник за выбранную дату: несколько записей в каждом приёме пищи. Форма сначала предлагает источник еды (полка, готовое блюдо, другая еда), затем количество. Дата и приём пищи видны сразу. Дата вводится текстом ДД.ММ.ГГГГ без системного календаря. Приём пищи по умолчанию зависит от времени дня, кнопка конкретного приёма сохраняет выбранный контекст. Готовые блюда можно записывать порциями, процентами и граммами при наличии измеренного или расчётного выхода. Календарь поддерживает прошлые недели и выбор месяца.
- Личный профиль с именем, возрастом, ростом и коллекцией достижений. Пожелания для рецептов задаются на главной. Старая история веса остаётся в сохранении для совместимости, в интерфейсе её нет.
- Фото/скриншот чека через «Полка → + → По чеку»: распознавание, проверка строк, уточнение массы и выбор КБЖУ, затем единое сохранение.
- ИИ-подбор по продуктам, пожеланиям, исключениям и времени. Результаты проверяются по составу/количествам и сохраняются локально. КБЖУ считает код по данным ингредиентов, а не модель.
- Бэкенд содержит 501 русский рецепт для каталога интерфейса, прежние 100 источников Based Cooking для контекста ИИ и 302 брендовых товара с КБЖУ/штрихкодами.

Прежние 100 рецептов Based Cooking — справочная база для модели: оригинальные ингредиенты и шаги на английском, названия также добавлены по-русски; ответ пользователю модель составляет по-русски. Точные граммовки, время и фотографии при импорте не выдумывались. Ручное добавление использует поиск по названию/бренду: типовые локальные продукты и до восьми результатов из серверного каталога после ввода запроса. Для внешней записи перед сохранением нужно проверить совпадение упаковки и основу значений на 100 г. Добавление каталожного продукта и запаса выполняется одним сохранением. Без опубликованного API остаётся локальный поиск.

Товары Open Food Facts — начальная выборка непроверенных данных сообщества. Пропуски не заменены догадками ИИ. Массу, единицы и совпадение конкретной упаковки нужно подтверждать перед использованием. Происхождение и ограничения: [документация каталога](apps/backend/README.md).

Старое поле `expiresOn` сохраняется в формате localStorage для совместимости и восстановления старых списаний, но не используется при подборе и не передаётся модели. Старый серверный бот с напоминаниями пока не переведён на новый сценарий; фронтенд его больше не вызывает.

## Что ещё не реализовано

Распознавание таблицы КБЖУ на упаковке и голосовой ввод; пополнение общей базы пользователями; полный российский ассортимент; семейные аккаунты; синхронизация устройств; напоминания о разморозке; автоматическая корректировка пищевой ценности при потерях в готовке. Кулинарная проверка всех импортированных рецептов не выполнялась.

## Проверки и сборка

```sh
npm run typecheck
npm test
npm run build
npm run build:backend
npm run check
```

`check` запускает TypeScript, тесты и обе сборки. `apps/web/dist` — статический фронтенд; `apps/backend/dist` — отдельный сервер/облачная функция. `npm run build:ai` оставлен как псевдоним сборки бэкенда.

Тесты ИИ используют заглушки и не расходуют квоту. Для отдельного реального запроса с вымышленными продуктами:

```sh
npm run build:backend
node --env-file=.env scripts/check-ai.mjs
```

При наличии `TIMEWEB_AI_TOKEN` используются платные модели Timeweb AI Gateway: `deepseek/deepseek-flash` для поиска/адаптации и `gemini/gemini-3.8-flash` для чеков. Переопределение — серверные `AI_TEXT_MODEL` / `AI_VISION_MODEL`. Старый Z.ai (`API_GLM`) используется только при отсутствии ключа Timeweb; при ошибке Timeweb скрытого переключения провайдера нет. Недоступность/429 модели показывается как ошибка, существующие записи не заменяются. Ограничение частоты — в памяти экземпляра; для публичной массовой эксплуатации понадобится отдельное решение.

## Размещение

Фронтенд: существующий `.github/workflows/pages.yml` собирает `apps/web/dist` для GitHub Pages. Settings → Pages → Source: GitHub Actions. `base: './'` поддерживает путь репозитория.

Для опубликованной ИИ-функции укажи полный URL в переменной репозитория `VITE_AI_API_URL`; workflow её читает. Без этого production-кнопка ИИ недоступна. `TIMEWEB_AI_TOKEN` (или прежний `API_GLM`) хранится только в окружении сервера. На сервере также нужны `ALLOWED_ORIGIN` и `BOT_TOKEN`. Публикация бэкенда описана в `apps/backend/README.md` и не выполняется сборкой.

Бот остаётся в `apps/bot`: команды `dev:bot`, `deploy:bot`, миграции и `wrangler.jsonc`. Не выполняй облачные миграции/деплой без отдельного решения. `scripts/setup-bot.mjs` меняет webhook и меню существующего бота — не является частью запуска фронтенда.

## Источники

Рецепты: [Based Cooking](https://github.com/LukeSmithxyz/based.cooking), Unlicense; источник и оригинал хранятся у каждого рецепта. Продукты: [Open Food Facts](https://openfoodfacts.github.io/openfoodfacts-server/api/), ODbL-1.0 / DbCL-1.0; производная выборка хранится отдельно с атрибуцией в API и документации. Фото продуктов из базы не скачивались.

Существующие фотографии рецептов сохранены: авторы/лицензии в `PHOTO_CREDITS.md` и `apps/web/src/data/photoCredits.ts`. Маскот — существующая иллюстрация груши; фотографии не заменялись эмодзи или генерациями.

## Чеки и обновление карточек

В локальной версии «Полка → +» открывает выбор «По чеку / Вручную». Распознавание использует `gemini/gemini-3.8-flash` через серверный `TIMEWEB_AI_TOKEN`; при отсутствии этого ключа сохраняется прежняя `glm-4.6v-flash` через Z.ai. Поддерживаются JPG, PNG и WebP (исходный файл до 12 МБ, после локального сжатия до 3 МБ). HEIC/PDF напрямую не поддерживаются. Фото хранится только в памяти формы и передаётся выбранному серверному провайдеру ИИ после нажатия кнопки, в localStorage изображения не сохраняются.

Результат — черновик. Пользователь проверяет названия, массу и источник КБЖУ, может убрать строки. Чётко указанные кг/г и упаковки пересчитываются кодом; миллилитры и штуки без массы остаются для уточнения. КБЖУ не извлекаются из памяти модели: предлагаются существующие типовые продукты и найденные записи каталога; для неизвестного товара можно выбрать аналог или ввести значения с упаковки. Типовые значения помечены как типовые, для брендовой записи с неоднозначными единицами требуется подтверждение 100 г. Добавление выполняется одним сохранением после проверки всех выбранных строк. Ошибка сохранения оставляет черновик открытым. Дневник при импорте не меняется.

Дизайн карточек, меток и навигации обновлён с сохранением бренда, шрифта и существующих фото. Референсы: [Mela](https://mela.recipes/) и [Crouton](https://crouton.app/); их ассеты в приложение не копировались. Дополнительные стили выделены в `styles/surfaces.css` и `styles/receipt.css`.

Для опубликованной версии нужно загрузить актуальный бэкенд: новый маршрут `/api/ai/receipt` (или `?route=/api/ai/receipt` у прямой Yandex-функции). Ключ остаётся серверным; вход через Telegram, CORS и лимиты общие с подбором рецептов. Визуальные изменения и распознавание не публикуются автоматически.

## Композиция экранов

Профиль объединяет личные данные, маскота и компактные показатели активности; отдельного блока «Под себя» и трёх карточек статистики больше нет. Дневник не показывает ссылку-плашку достижений. Шапка полки называется «Запасы», действие «Добавить» выровнено с заголовком. Создание продукта по значениям с упаковки доступно через «Добавить → Вручную → Не нашёл продукт? Добавить новый»; отдельная кнопка внизу полки удалена.

Главная сохраняет заголовок и основную кнопку подбора. Поле пожеланий оформлено как записка без ручного растягивания; время вводится вручную в минутах (5–360). Ниже — список готовых блюд с прямым переходом к записи порции. Стили композиции — `styles/composition.css`, страницы рецепта и форм — `styles/cooking.css`.

В `components/food-art/` — 24 локальные векторные иллюстрации: отдельные рисунки для всех исходных продуктов и дополнительных категорий (овощи, фрукты, рыба, хлеб, грибы и другие). Для новых товаров тип иллюстрации определяется по названию, при неизвестном названии используется нейтральная банка. Фотографии рецептов не менялись.

## Уточнение главной и форм

На главной логотип и груша собраны в одну шапку; отдельные конкурирующие заголовок/подзаголовок убраны. Заголовок сценария — «Что хочется сегодня?». В карточках с нехваткой нескольких продуктов отображаются их количество и до трёх названий; полный список с граммами — внутри рецепта. Подборка запроса показывает три карточки и кнопку «Смотреть все N рецептов»; полный список загружается страницами на отдельном экране. Топ‑3 на главной остаётся из небольшого исходного набора. Полная выдача нового русского каталога открывается отдельно, без ограничения в шесть результатов. Кнопка «Приготовил своё блюдо» с главной удалена.

Ручной ввод на полке — поиск → выбранный продукт → количество. Для яиц доступны штуки без инструкции о скорлупе; база продолжает хранить граммы для расчётов. Подпись о точках в календаре дневника удалена.

## Поведение ИИ при ошибках

Кнопки отмены подбора и распознавания имеют размер основной кнопки и абрикосовый цвет. Стрелки числового поля времени скрыты. Сообщение о временной ошибке ИИ закрывается крестиком, автоматически скрывается через 12 секунд и сбрасывается при изменении запроса/фото. Неудача сохранения остаётся видимой; черновик и фото не удаляются.

Подбор принимает только проверенные рецепты из известных продуктов, однозначные числовые строки нормализуются. Если все рецепты некорректны, сервер один раз просит ту же бесплатную модель исправить ответ. Частичный успешный ответ может содержать меньше трёх рецептов. Для явного «из творога» при однозначном совпадении на полке творог обязателен в каждом принятом варианте. Сервер различает перегрузку, ограничение частоты, квоту и доступ к модели; один временный отказ автоматически повторяется. Это не гарантирует доступность внешнего бесплатного сервиса.

## Большая выдача рецептов

В интерфейс подключён открытый каталог [UniTools](https://theunitools.com/ru/data): **501 рецепт на русском**, лицензия CC BY-SA 4.0. Импорт и ограничения описаны в [документации бэкенда](apps/backend/README.md#русский-каталог-для-интерфейса). Прежние данные и реальные пользовательские сохранения не заменяются.

«Что хочется сегодня?» сначала передаёт пожелание ИИ: модель выделяет название блюда, обязательные ингредиенты, исключения, категорию, диету и сортировку. Код применяет эти условия ко всей базе из 501 рецепта, учитывая время и полку. На главной отображаются три результата, общее число найденного и переход ко всем результатам. Если точного совпадения нет, ИИ может адаптировать конкретный рецепт из этой же базы. Рецепты без известного источника не принимаются.

Отдельного входа в каталог на главной нет: полная выдача открывается кнопкой «Смотреть все N рецептов» после запроса. На отдельном экране «Поиск по базе» уточняет выдачу по названию блюда или ингредиентам без нового вызова ИИ. Категории выбираются в прокручиваемой строке. Лимит времени вводится вручную, применяется по Enter или при выходе из поля; пустое поле означает любое время. Есть сортировка, сброс фильтров и загрузка страниц по 12. Изменение фильтра не отправляет недописанный текст поиска. Верхнего ограничения в 6/12/100 нет: можно дойти до всех 501 записей. Счётчик отражает реальные результаты, а возврат из рецепта сохраняет загруженные страницы и позицию. Персонализация трёх домашних идей по истории поведения пока не реализована.

Исходный рецепт открывается целиком на русском, с порциями, единицами ингредиентов и примерными значениями КБЖУ из источника. Это не расчёт по конкретным упаковкам пользователя. Для списания по полке есть отдельная подготовка через ИИ: после неё открывается редактируемый рецепт с расчётом КБЖУ по локальному каталогу и прежним раздельным приготовлением/приёмом пищи. Адаптация зависит от доступности Z.ai.

Для GitHub Pages сборка автоматически кладёт статический снимок публичного каталога в `dist/catalog/recipe-library.json`. Он загружается отдельно от JS, при открытии каталога; чтение каталога и пагинация работают без API каталога. Начальный подбор по свободному пожеланию требует доступного ИИ API; лексический поиск не подменяет его при ошибке. В dev/с подключённым API используются серверные страницы, со статическим fallback. Серверный JSON остаётся единственным исходником данных; снимок формирует `scripts/build-library-snapshot.mjs`, импорт из интернета во время сборки не запускается. Настройки облаков и публикация не менялись.

## Подстановка КБЖУ из чеков

Локальная серверная база расширена до 302 брендовых записей Open Food Facts; типовой каталог — до 50 продуктов (13 прежних и 37 овощей/фруктов из справочных таблиц FDA). Данные не генерируются нейросетью. Новый ограниченный импорт: `npm run import:products` (три выборки до 100 исходных строк), отчёт — `apps/backend/data/nutrition-import-report.json`. Повтор старого импортера сохраняет уже собранные продукты.

После OCR сервер сопоставляет название без веса упаковки и лишней пунктуации, проверяет жирность и различает уверенное совпадение бренда и похожие варианты. Уверенный товар/типовой аналог подставляется в черновик автоматически. Несколько похожих упаковок предлагаются на выбор. Ввод четырёх значений КБЖУ открывается по действию «Нет подходящего — ввести с упаковки», а не для каждого товара. Сохранённый пользователем продукт повторно используется при совпадении названия; общая база на сервере из личных данных не пополняется.

Уточнение массы остаётся, если её нет в чеке. Для жидкости или неясной основы значений остаётся подтверждение 100 г; для однозначных твёрдых категорий оно не требуется. Типовые значения не выдаются за точные значения конкретной упаковки. Источники и ограничения — в [документации бэкенда](apps/backend/README.md#автоподстановка-пищевой-ценности).

Удалены отдельная кнопка каталога, подпись под «Запасы», инструкции о подтверждении фото и повторные пояснения уже понятных действий. «Идеи для тебя» остаются тремя демонстрационными карточками; персонализация по истории запланирована, сейчас не реализована.

## Telegram-вход и пользовательские данные

Вход при открытии Mini App проверяет Telegram `initData`, создаёт или открывает свой аккаунт и загружает серверные данные. Локального обхода подписи для аккаунтов нет. Сессия живёт 7 дней; в БД хранится только SHA-256 хеш случайного токена. Помимо Secure HttpOnly cookie есть сессионный токен только в памяти приложения для Telegram-фреймов, блокирующих cookies; он не записывается в localStorage. Фронтенд и API размещаются на одном origin с путями `/` и `/api`.

Настоящий аккаунт начинает с пустой полки и именем Telegram. Старое локальное сохранение предлагается перенести только в ещё не изменённый серверный аккаунт, после явного подтверждения владельцем; исходная копия не удаляется. Ошибка авторизации или БД не подменяется успешным входом в демо. Напоминания не развиваются, рабочий бот не переключается. Без `DATABASE_URL` настоящий аккаунт не открывается.

`GET /api/state` и `PUT /api/state` сохраняют полку, готовые блюда, дневник, личные продукты, профиль, настройки и адаптированные рецепты. Версионированный JSONB-агрегат принадлежит одному пользователю; изменение всех разделов и запись номера операции выполняются одной транзакцией. Старый revision даёт 409 с актуальным состоянием, повтор той же операции не применяет её дважды. Неподтверждённый запрос хранится отдельно по серверному UUID аккаунта в localStorage и повторяется с тем же ID и содержимым, в том числе после перезагрузки. Формы ожидают подтверждения, при конфликте пользователь видит обновлённые данные и повторяет действие сам. Подробности и ограничения — [USER_DATA.md](USER_DATA.md).

Локальная БД через установленный и запущенный Docker:

```sh
npm run db:up
```

В корневой `.env` добавить `DATABASE_URL` из `.env.example`, а `BOT_TOKEN` — настоящий токен своего бота. Секреты не отправлять в чат. Данные БД остаются в именованном Docker volume после остановки. Пароль из compose предназначен только для локальной разработки с привязкой порта к 127.0.0.1; его нельзя использовать на хостинге.

```sh
npm run db:migrate
npm run dev
```

Миграции не применяются автоматически при запуске приложения; повтор команды безопасен, редактирование уже применённого SQL обнаруживается по контрольной сумме. Создавайте следующий файл миграции. `npm run db:stop` останавливает БД, не удаляя volume.

`npm run test:database` запускает отдельные интеграционные проверки. Нужен `TEST_DATABASE_URL` на специально созданную тестовую базу (название содержит `test`). Тесты не читают `DATABASE_URL`, используют случайную временную схему и удаляют только её. Без тестового URL эти проверки явно пропускаются; обычные тесты доступны без PostgreSQL.


## Голосовое добавление продуктов

«Полка → Добавить → Голосом» и стартовое «Разобрать холодильник» используют один сценарий. Можно диктовать или писать, отвечать на уточнения и проверить список перед сохранением. Кнопка завершения или отдельное «всё» открывает проверку; пауза не добавляет продукты автоматически. КБЖУ берутся из каталога, примерные бытовые массы явно помечены. Сырые аудиозаписи в хранилище приложения не сохраняются. Для аудио нужен серверный `TIMEWEB_AI_TOKEN`; `AI_SPEECH_MODEL` можно переопределить. Подробности и ограничения — [бэкенд](apps/backend/README.md#голосовое-заполнение-полки).


## Первый вход и интерфейс

Первый экран — отдельная страница без обязательной анкеты: голос, чек или ручной ввод продуктов; можно пропустить. Имя берётся из подтверждённого Telegram-аккаунта, дополнительные данные профиля меняются по желанию. Старые демозаписи при входе не предлагаются и не копируются в аккаунт; исходные локальные данные не удаляются. Для собственных прежних записей остаётся явное подтверждение переноса. Поля тестового доступа убраны из пользовательских форм; серверная авторизация сохранена.

Главное действие — «Что приготовим?» → «Найти рецепты», с редактируемым текстом или голосом. Общая система экранов и мобильных отступов — `styles/experience.css`; существующие фотографии и иллюстрации сохранены.
