# Аккаунты и пользовательское хранилище

## Что реализовано

При открытии из Telegram фронтенд передаёт raw initData только своему серверу. Сервер проверяет HMAC, давность и подписанный Telegram ID, создаёт/находит аккаунт и сессию. Непроверенный `initDataUnsafe.user.id` никогда не авторизует доступ к БД. Cookies — HttpOnly, Secure в production, SameSite=Lax; дополнительно выдаётся непрозрачный сессионный токен, который фронтенд держит **только в памяти**, для клиентов Telegram с заблокированными cookies. В PostgreSQL хранится только его SHA-256 хеш. Это токен сессии пользователя, не токен бота. Выход отзывает текущую сессию, остальные устройства остаются авторизованными.

Публикация `/api/state` не открывает чужие данные: пользователь определяется по действующей сессии. `accountId` в PUT — дополнительная проверка, что cookie/токен не сменился во время запроса; он не выбирает владельца записи. Чужой origin, отсутствие сессии или несовпадение аккаунта отклоняются. Ответы аккаунта и состояния — `Cache-Control: no-store`.

## Схема и атомарность

- `polka_users`, `polka_sessions`: аккаунты и семидневные сессии (миграция 001).
- `polka_user_states`: один JSONB-документ на аккаунт, целочисленная ревизия и время изменения (миграция 002). Типизированные разделы: полка, приготовленные блюда, дневник, личные продукты, профиль, настройки, адаптированные рецепты.
- `polka_state_writes`: ID подтверждённых операций, хеш запроса и применённая ревизия. ID уникален **внутри аккаунта**.

Текущий объём данных не требует разнесения каждого поля по таблицам. Версионированный агрегат позволяет сохранить списание сырья, создание блюда и изменения дневника целиком, без промежуточного состояния. Каталоги рецептов и общих продуктов не смешиваются с личными данными. Слой `src/state` можно заменить отдельными предметными таблицами и командами без изменения авторизации.

GET создаёт пустое состояние только при отсутствии записи, с именем из проверенного аккаунта, без демопродуктов и фиктивной истории. PUT получает `{ accountId, revision, mutationId, state }`, проверяет структуру, разумные числовые границы, даты, уникальность ID, ссылки на продукты и блюда, суммарные съеденные доли и остаток. Одна транзакция блокирует строку, проверяет квитанцию операции, сверяет ревизию, сохраняет все разделы и квитанцию, обновляет признак знакомства. Ошибка любого SQL откатывает всё.

При двух конкурентных сохранениях с одинаковой ревизией проходит одно; другое получает 409 с актуальными данными. Повтор **того же** запроса возвращает уже сохранённое состояние без повторного применения. Повтор ID с другим содержимым отклоняется. Старый повтор после изменений другого устройства возвращает последнее состояние, а не воскрешает прежнее.

## Ошибки сети и прежние записи

Перед отправкой подтверждённого действия фронтенд сохраняет его точный запрос в `polka:account:<серверный UUID>:pending-v1`. Это черновик неподтверждённого сохранения, не основное хранилище аккаунта. До подтверждения форма остаётся открытой, сообщение об успехе не показывается. При обрыве связи, таймауте, 401 или 503 черновик остаётся; пользователь повторяет отправку с тем же ID/ревизией/содержимым. После перезагрузки проверка проводится до открытия основного интерфейса. Черновики других аккаунтов не читаются. Если локальное сохранение черновика не удалось, запрос не отправляется и форма сообщает об ошибке.

При конфликте клиент обновляет состояние сервера, показывает ошибку и оставляет форму, чтобы владелец заново проверил количество/остаток. Действие не переигрывается автоматически поверх чужого изменения. Детерминированно отклонённые запросы не отправляются бесконечно.

При первом входе в ещё не изменённый серверный аккаунт можно выбрать прежнее сохранение этого Telegram ID либо явно подписанное сохранение браузера. Перед переносом показаны имя, тип сохранения и число продуктов/записей/блюд. Нужна кнопка подтверждения владельца. Другие Telegram-ключи не предлагаются. Демоданные обозначаются как демонстрационные. Исходная локальная копия не удаляется, не сдвигается по датам и не перезаписывается. Если сервер изменился во время переноса, повторное нажатие не должно перезаписать его: открываются актуальные данные с сообщением о конфликте.

Отказ от переноса открывает пустую серверную полку; позже автоматическое смешивание с уже заполненным аккаунтом не выполняется. Отдельный инструмент слияния существующих историй пока отсутствует. Новые серверные записи имеют исходные даты; механизм актуализации демонстрационных дат применяется только к локальному демо.

## Запуск и границы готовности

Нужны серверные `BOT_TOKEN`, `DATABASE_URL`, точный `ALLOWED_ORIGIN` и обе миграции:

```sh
npm run db:migrate
npm run dev
```

Локальный браузер без подписанного Telegram-контекста сохраняет удобный деморежим для разработки. В production ошибка БД/входа не подменяется демо: показывается экран входа, демо выбирается отдельно. Для настоящего входа нужен запуск Mini App через бота на HTTPS-домене. Инструкция Timeweb — [DEPLOYMENT.md](DEPLOYMENT.md). Ключи не отправляются в чат и не добавляются в Git.

Серверное хранилище реализовано и проверяется локально; облачная PostgreSQL ещё не создана, данные настоящего пользователя автоматически не переносились. Рабочий бот и webhook не перенастраивались. Расчёты и построение действий пока выполняются существующими доменными функциями клиента; сервер валидирует и атомарно сохраняет результат. Это не реализация отдельных серверных команд для каждого ингредиента. Обновление другого уже открытого устройства видно после повторного открытия либо обнаружения конфликта; push-синхронизации в реальном времени нет. Для больших историй потребуется постраничное хранение/выдача; текущая версия ограничивает тело сохранения 4 МиБ, до 10 000 записей дневника, 5 000 блюд, 2 000 партий продуктов, 3 000 личных продуктов.

Источники: [проверка initData Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), [транзакционная изоляция PostgreSQL](https://www.postgresql.org/docs/16/transaction-iso.html). Реальное поведение Telegram Android/iOS/Desktop после внешнего подключения ещё нужно проверить; локальные тесты не объявляются такой проверкой.
